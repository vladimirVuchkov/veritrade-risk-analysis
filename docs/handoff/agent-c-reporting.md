# Handoff - Agent C (Reporting)

## Done
- **Domain and repositories** (`domain`, `repository`): `Report` (one row per filing; ordering and per-category and per-severity counts), `FindingEntity`, `ProcessedEvent`, `ReportStatus`, and `ColumnText`, which fits text to a column. Hibernate validates the entities against the fixed `V1__init.sql` (`ddl-auto: validate`).
- **`AnalysisResultListener`** (`messaging`): one `@RabbitListener` on `reporting.analysis-results`. It takes the raw AMQP `Message`, so no message converter and no `__TypeId__` header is involved. `AnalysisEventReader` dispatches on the `eventType` field, or on the routing key when that field is absent. It is a tolerant reader: unknown fields are ignored and declared fields are required. `AnalysisEventValidator` checks the schema rules Reporting relies on: required fields, non-negative numbers, enum values, and text limits counted in code points. It also rejects an `eventVersion` newer than `EventEnvelope.CURRENT_VERSION`. The `correlationId` (the AMQP property, then the envelope value) goes into the MDC under `CorrelationIds.MDC_KEY` and is removed afterwards.
- **`IdempotencyGuard`** (`service`): its methods are `Propagation.MANDATORY`, so `processed_events` is written in the same transaction as the report. A failure rolls back both, and this is tested.
- **First terminal event wins** (`ReportService`): a duplicate `eventId` returns `DUPLICATE`. Any other terminal event for a filing that already has a report returns `IGNORED_LATE` and logs a WARN with the eventId, the filingId and both states. That covers the same type with a different eventId, completed then failed, and failed then completed. Both outcomes are acknowledged; nothing is thrown.
- **`ReportService`**: stores a report keyed by `filingId`, with `totalFindings` and `overallRiskLevel` taken from the event summary. `byCategory` and `bySeverity` are computed from the stored findings. Findings are ordered by severity (highest first), then by position.
- **`ReportController`**: `GET /api/reports/{filingId}` returns the OpenAPI `ReportResponse`. Until the report is ready it returns a 404 `ProblemDetail`. A malformed id also gets a 404 `ProblemDetail`, because the OpenAPI defines only 200 and 404 for this operation. `spring.mvc.problemdetails.enabled=true` is set for the remaining MVC errors.
- **`RabbitConfig`**: declares exactly the documented topology: `veritrade.events` (topic), `veritrade.dlx` (direct), and the durable `reporting.analysis-results` queue with only `x-dead-letter-exchange` and `x-dead-letter-routing-key`. It also declares the `.dlq` with no arguments, its binding on `veritrade.dlx`, and the `analysis.completed` and `analysis.failed` bindings. A `RabbitListenerRetrySettingsCustomizer` marks `AmqpRejectAndDontRequeueException` (our `InvalidEventException`) and `MessageConversionException` as not retryable, anywhere in the cause chain. Such messages go to the DLQ at once through the Boot `RejectAndDontRequeueRecoverer`.
- **Configuration**: `max-retries: 2` (= 3 attempts) replaces the removed `max-attempts`. `@ConfigurationProperties("reporting.limits")` holds the contract and column limits.
- **Text longer than its column** (orchestrator note 3): text within the contract limit in code points can still exceed the VARCHAR size in UTF-16 units (emoji, for example). `ColumnText.fit` shortens it without splitting a surrogate pair. Text over the contract limit is invalid and goes to the DLQ without retries. Neither case returns a 500 or loops on retries.
- **Tests**: 134 unit tests (`*Test`) and 17 integration tests (`*IT`, Testcontainers `rabbitmq:4.3-management-alpine`), all green.
  - `AnalysisEventReaderTest` (77): both contract examples; unknown fields at every level; dispatch on `eventType` against a wrong routing key and a lying `__TypeId__`; the routing-key fallback; unknown or unsupported event types; malformed and non-object JSON and non-UTF-8 bytes; every missing or null envelope, payload, summary and finding field; unknown enum values; every `RiskLevel`, including `NONE`, every `Severity` and every `RiskCategory`; zero findings; text exactly at each limit and one past it; limits counted in code points.
  - `ReportServiceTest` (21, real Flyway schema in H2 with test-managed transactions off): duplicate eventId; same filing with a new eventId of the same type; completed then failed, and failed then completed; interleaved out-of-order events of two filings; zero findings with `NONE`; every `RiskLevel`; every severity and category; 1,500 findings; values exactly at the column sizes; emoji text fitted without split pairs; rollback of `processed_events` on a DB constraint failure and on a repository exception, with the retry then succeeding; the guard refusing to run outside a transaction.
  - `AnalysisResultListenerTest`, `RabbitConfigTest`, `ReportTest`, `ColumnTextTest`, `ArchitectureTest` (layers, a Spring-free domain), and `ReportingApplicationTest`.
  - `ReportControllerTest` (`@WebMvcTest`): 200 bodies for COMPLETED, NONE and FAILED, each validated against `components/schemas/ReportResponse` of `rest-api.openapi.yaml` with the networknt validator. Also covers the 404 `ProblemDetail` (validated against the `ProblemDetail` schema), malformed ids, a 405 `ProblemDetail`, and a sanity check that the schema rejects bad bodies.
  - `ReportingFlowIT`: publishes `analysis-completed.json` and checks that the report has the example's findings, `totalFindings`, `overallRiskLevel` and `byCategory`, plus `bySeverity` and OpenAPI validity. It also covers double delivery giving one report, `analysis-failed` giving a FAILED report, a late contradictory event being acked and not dead-lettered, and a 404 before any event.
  - `DeadLetterIT`: malformed JSON, `[]` and an unknown `eventType` each reach `reporting.analysis-results.dlq` after exactly one read. A payload missing `summary` is dead-lettered as well. A processing failure is attempted exactly 3 times, takes at least 3 s of backoff, and is then dead-lettered (`x-death` reason `rejected`) with no report and no processed marker.
  - `TopologyIT`: checks the exchanges, queues, arguments and bindings through the management API. Redeclaring with the documented arguments is idempotent; a redeclaration with different arguments is refused.
  - `RestartIT`: two application runs on one H2 file in a temporary directory. The report and the processed marker survive the restart, a redelivery after the restart stays a duplicate, and a new report can be inserted after the restart.

## Known issues and limitations
- **Requests to the orchestrator:**
  1. The OpenAPI path is `/api/reports/{filingId}`, and PLAN 6.3 writes `GET /reports/{filingId}`. I implemented the OpenAPI path, so nginx (Agent E) must proxy `/api/reports` without stripping `/api`.
  2. The OpenAPI has no 400 for `getReport`, so a malformed id returns a 404 `ProblemDetail`. If a 400 is wanted, the contract needs a `400` response there.
  3. The summary's `byCategory` in the event and the computed one can disagree when `summary.totalFindings` differs from `findings.length`. The contract does not say whether the summary counts capped findings. Reporting trusts the event for `totalFindings` and `overallRiskLevel` and computes `byCategory` and `bySeverity` from the findings it stores. Please confirm with Agent B that `totalFindings` equals the number of findings published.
- **H2 2.4.240 CHECK-constraint bug** (orchestrator note 1): not reproduced in Reporting's tests. `RestartIT` inserts into `reports` (which has a CHECK) after a restart on a file database, and it passed. No workaround is in the code. Pinning 2.3.232 at merge time remains the safe choice.
- `generatedAt` is the time Reporting stored the report (UTC `Clock`), not the event's `analyzedAt` or `failedAt`.
- An event with an `eventVersion` above 1 is dead-lettered, so it can be replayed after an upgrade. A message with an event type Reporting does not consume (`FILING_SUBMITTED`, `ANALYSIS_STARTED`) is dead-lettered as misrouted; the bindings prevent this in normal operation.
- Reporting does not publish, so it declares no `JacksonJsonMessageConverter` bean. The listener reads the raw body with the Spring Boot `JsonMapper`.
- RabbitMQ 4 reports a server-added `x-queue-type: classic` argument on queues. Reporting does not declare it; `TopologyIT` ignores exactly that default.
- Integration tests share one broker container, but each test class uses its own virtual host. Spring keeps cached test contexts and their listeners alive, so without separate virtual hosts they would compete for messages on the same queue.
